## Bug 修复：编排↔3D 切换后工辅设施无法对应工艺
**现象**：编排模式与 3D 数字孪生反复切换后，工辅设施↔工艺的对应关系丢失/错乱（3D 物料管廊消失或不对应）。
**根因**：设施→工艺对应只有一处真源——`scheme.connections`（编排时画的线）；3D 孪生只读 `facilityLinks`（在 `exitEdit→autoLayoutAux` 反算）。`enterEdit()` 调 `modelToScheme()` 从 `model` 重建方案时**只重建工序节点与工序间物流，把设施→工艺连线整个丢弃**；`_seedFacilityNodes()` 只补回设施节点不带连线。于是再次进入编排时设施是断开的，退出时 `autoLayoutAux` 反算出的 `facilityLinks` 也变空，3D 管廊随之消失。
**修复**（`frontend/src/stores/sim.js`，已 `node --check` 通过）：
1. 新增 `_restoreFacilityConns()`：进入编排时，从已持久化的 `facilityLinks` 反向回填「设施→工艺」连线（按物料精确匹配，其次同物料族匹配端口；输入口去重，与 `addConnection` 一致）。
2. `enterEdit()` 在 `_seedFacilityNodes()` 之后调用 `_restoreFacilityConns()`。
3. `facilityLinks` 与 `facilityLayout` 一并持久化到 localStorage（`_saveFacilityLinks` / `_loadFacilityLayout` 内加载），使 3D 物料管廊跨刷新也保持。`facilityLinks` 以稳定工序 id（preset 固定 s1/bf1/bof1/...）为键，安全。
**验证要点**：连线只发生在有匹配输入端口的设施（焦化→coke、发电→self_power、制氧→oxygen 等），其余设施（水处理/办公/铁路 outputs 为空）本就不应连线；restore 对不存在的工序节点会跳过，不会串到错误工艺。

## Bug 修复：前端「命令行窗口」报「模型未配置或未连通」
**现象**：用户在浏览器命令行窗口发消息，后端返回「模型未配置或未连通：请在后端设置 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL 后重启」。
**根因（两层）**：
1. 后端是**本地直接跑**的（`backend/run.sh` → `uvicorn app.main:app --port 8010 --reload`，PID 曾为 9096），**不是 docker**。`docker-compose.yml` 里的 `LLM_*` 只在容器启动时注入，本地进程根本拿不到 → `_call_llm` 因 `api_key` 为空直接 return None。
2. 本机 `HTTPS_PROXY` 是 http://127.0.0.1:PORT（端口会变，本次 49258）。即便有 key，`urllib` 也会把对 `api.deepseek.com` 的调用交给本地代理而失败。
**修复**（`backend/app/llm_strategy.py`）：
- 新增 `_load_dotenv()`：进程启动时（模块顶层调用）从 `backend/.env` 与项目根 `.env` 读取并补进 `os.environ`，使 `run.sh` 这类未导出 `LLM_*` 的本地启动也能拿到配置（配置优先级：进程环境变量 > .env > 默认值）。
- `_call_llm` 改用惰性 `_llm_cfg()` 读取（支持 .env 兜底）；用 `urllib.request.build_opener(ProxyHandler({}))` 显式**绕过本机代理**直达外部 API。
- 已新建 `backend/.env`（含三项 LLM_*），故 `run.sh` 重启即生效，无需手动 export。
**验证**：把后端以持久后台任务（run_in_background）重启并导出 `LLM_*`，`curl -s --noproxy '*' POST /api/chat` 返回 `{"ok":true,...,"reply":"..."}`（HTTP 200，chat 与 sty 模式均通）；`py_compile` 通过。
**重要环境注意（本机）**：Bash 工具里后台进程在命令结束时会被回收，**本地服务器/后端必须 `run_in_background:true` 才能跨工具调用存活**（与静态服务器+Chrome 同理）。本机 proxy 端口会变，curl 一律 `--noproxy '*'`，Python urllib 已用 ProxyHandler({}) 兜底。

## 代码同步到服务器（部署流程，可复用）
**本项目不是 git 仓库**，与服务器同步靠 rsync。目标：`root@172.19.134.45:/root/qzb/jianpai/`（SSH 免密可用；曾在隔离网络下超时，先测连通再传）。

标准命令（在项目根执行）：
```
rsync -az --delete --checksum -i --stats \
  --exclude 'node_modules/' --exclude '.venv/' --exclude 'venv/' \
  --exclude '.workbuddy/' --exclude '__pycache__/' --exclude '*.pyc' \
  --exclude '.git/' --exclude '.DS_Store' --exclude '*.log' \
  --exclude 'frontend/.vite/' --exclude 'vite.config.js.timestamp-*.mjs' \
  --exclude '.serve_check.mjs' --exclude '_t_compute.mjs' \
  --exclude 'backend/1necho' --exclude '__test.html' \
  -e 'ssh -o StrictHostKeyChecking=no' ./ root@172.19.134.45:/root/qzb/jianpai/
```

**三个关键经验**：
1. **必须加 `--checksum`**。`npm run build` 会把 `public/models/*.glb` 重新复制到 `dist/models/`，mtime 变了但内容没变；不加 checksum 会白传 92MB（含 49MB 的 gaolu_opt.glb），加了只传 4.4MB。
2. **传完必须 `docker compose restart steel-twin`**。容器用 bind mount + `uvicorn --reload`，但 **rsync 的写入不会触发容器内 watchfiles 的 inotify**——本次传完后 `/api/param-schema` 仍返回旧 schema（缺 `electricity`），容器内文件却已是新的，重启后才生效。这是最容易漏判的一步。
3. **本地有垃圾文件需排除**：`frontend/vite.config.js.timestamp-*.mjs`（36 个，vite 崩溃残留）、`backend/1necho`（命令 typo 产物）、`.serve_check.mjs`/`_t_compute.mjs`（调试残留）。本环境 safe-delete 钩子拦截 `rm`，删不掉就在 rsync 里排除。

**部署后验证清单**：`docker ps` 状态 → `docker logs --tail` 无报错 → `/api/health` 200 → `curl /` 返回的 `assets/xxx.js` 与 `dist/index.html` 一致且文件存在 → `/api/param-schema` 含本轮新增字段 → POST `/api/simulate`（用 `/api/model/preset` 的模型作 body，**空 `{}` 会 422**，非 bug）应返回 `baseline/strategy/delta`，baseline.units 6 个工序、高炉 ≈13891 tCO₂/h。

本次结果：上传 56 文件/4.4MB，清理服务器陈旧文件 115 个（含大量历史 `dist/assets/index-*.js|css`、已废弃组件 `DevicesPanel/HudBar/LegendPanel/FactorsPanel/ExperimentPanel/PalettePanel.vue`、无引用的 `equipment_01_opt.glb`——已确认 `scene.js` 只引用 6 个 glb）。访问地址 `http://172.19.134.45:40014`。

## 右侧属性面板去粗体（仅块标题保留粗体）
**根因**：`main.css` 有全局 `b, strong { font-weight: 600 }`（第 34 行），所有 `<b>` 默认 600。此前组件内把值设成 `font-weight:500`，但两点问题：(1) 字体若无 500 档会回退到 700（真粗体）；(2) 部分 `<b>`（RightInspector `.chip2 b`、FlowInspector `.pr-top b` 等）根本没对应规则，直接吃全局 600 → 看着就是粗体。
**修复**：在 `main.css` 加 `.inspector` 作用域规则（仅限右侧面板）：`.inspector b, .inspector strong` 及 `.cb-badge/.tech-btn.primary/.adj-val/.pc-t/.note .hl/.pr-top b/.bal-item b/.dev-meta b/.ltr-top .it/.trend-foot b/.cb-target b/.cb-row>b` 全部 `font-weight:400 !important`；块标题 `.ctitle/.ttl/.insp-title/.blk-label` 显式 `600 !important`。同时把全局 `.kv2 b/.chip2 b/.kv b` 及组件内残留 `500` 清理为 `400`。

## 3D 孪生：写实 → 示意剖切模式（看清内部热量/管道）
用户核心诉求：原模型过于"照片级写实"（封闭金属外壳 + 大气雾 + 真实 GLB），导致内部状态（分层的温度、管道内物料）被藏住，不适合做 AI 数字孪生。需求是"不一定要逼真，但要能说明各流程特性、可视化内部情况"。

改造（frontend/src/three/scene.js 为主战场）：
- 双渲染模式开关 `renderMode`（默认 `schematic` 示意剖切 / 可切 `realistic` 写实园区）。构造器 `new TwinScene(host, {renderMode, envMode})`；新增 `setRenderMode()` 运行时切换（重建舞台+模型）。
- 环境：`_applyStage()` 分支——schematic 关闭天空/外围景观/雾/PMREM 环境反射，背景纯净浅灰；`_initGround()` schematic 仅留地坪+主干道，去掉绿化/树丛/铁路/围墙。
- 设备外壳：schematic 下外壳半透明（opacity 0.20, depthWrite false, DoubleSide）+ `_schematicizeBody` 描边（EdgesGeometry 工程线框感）；真实 GLB 仅 realistic 启用。
- **热量分层可视化（`_addHeatLayers`）**：容器类工序（高炉/转炉/EAF/LF/连铸/加热炉）内部按高度生成 16 层温度色柱（蓝→青→绿→黄→橙→红→白热 色阶 `_tempColor`），侧旁同色温度标尺 + 顶/底温度精灵；`_tempProfile` 按工序类型给示意温度剖面（高炉底热顶冷、连铸顶热底冷…），预留 `res.bottomTemp/res.topTemp` 真实遥测接口；动画 `tick` 脉动、`updateHeat` 接实时热度。
- 管道内容：沿用既有半透明管壳+彩色载运体+物料标签（已能表达管内介质）；`updateHeat` 同步刷新热量分层。
- UI：`sim.js` 加 `renderMode/renderModeNonce/setRenderMode`；`SceneViewer.vue` 传参+监听切换；`App.vue` 主页加「渲染模式」段（示意剖切/写实园区 两个按钮）。

验证：`vite build` 通过；无头 Chrome（swiftshader）加载后端 8010：无 JS 报错、3D 未回退、UI 按钮生效；临时插桩确认运行时为 eaf/ladle_furnace/rh_vacuum/caster 共 4/5 台容器设备生成了温度分层（heatUnits 4），移除插桩后重建干净。

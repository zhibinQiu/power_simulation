# 外部数据接入指南（数据中间件）

> 目标：把**任意外部数据源**（业务系统 MQTT、数据中台、仪表/PLC 网关、模拟数据源…）
> 接入能碳平台，与能碳一体机数据在同一条摄取管道里按前缀区分归属。
>
> 一句话：**外部数据不直接对接平台**——先注册到「能碳数据中间件」，由中间件采集并
> 转换为标准 MQTT 发布到**云端 Broker（41883）**，平台按 `box` 前缀识别归属。
> **平台与中间件自身都不产生模拟数据**，模拟由独立服务 `sim-source` 提供。

---

## 1. 整体架构

```
外部数据源（仪表 / PLC / 数据中台 / 第三方业务系统）
        │  网线 / 工业总线接入（现场常见形态）
        ▼
能碳一体机（边缘盒子：采集 + 透传上报）
        │  上行原始主题：ext/<源>/<设备>/telemetry（载荷任意 JSON）
        ▼
云端 Broker :41883 ── 上行空间 ext/#
        │  数据中间件订阅上行空间并转换（mqtt 适配器）
        ┌──────────────────────────────────────────────┐
        │ 能碳数据中间件（服务器 /opt/nengtan-middleware）│
        │  · 注册中心 registry（config.json 持久化）     │
        │  · 适配器 adapters（当前：mqtt）               │
        │  · 输出桥 bridge（external：直发云端 Broker）   │
        │  · 管理 API :42084（平台在此注册/启停数据源）   │
        └──────────────────────┬───────────────────────┘
                               ▼ 标准主题：data/{box}/{device}/{device}/{property}
                 云端 Broker :41883 ── 标准空间 data/ext-*
                               ▼
   平台摄取 → 按 box 前缀识别归属 → 启停过滤 → 最近读数/设备统计
```

> **平台只消费标准空间**：`ext/#` 是「一体机 → 中间件」的上行原始空间，平台**不摄取**
> （避免同一条数据被收两次、避免建出无归属设备）；平台只处理中间件转换后的
> `data/ext-*/…`。开发/演示用 `sim-source` 模拟「一体机上行」这一段
> （主题 `ext/steel/#`、`ext/idc/#`）。

三个关键约定：

1. **归属靠前缀**：平台按标准主题第二段（`box`）判断这条数据属于哪条数据源；
   前缀在平台「数据源接入」里登记（推荐 `ext-` 开头，如 `ext-weigh`、`ext-steel`）。
2. **转换只在中间件**：平台不解析外部协议，外部系统/一体机上行什么格式都行，
   中间件负责展平/改名/取设备 id/归一时间，输出平台能识别的标准消息。
3. **上游入口是能碳一体机**：外部数据源通常经网线接入一体机，由一体机把原始数据
   上行到云端 Broker 的 `ext/<源>/#` 空间；中间件订阅该空间做转换。
   若外部系统自带 Broker 且不经一体机，中间件也可直连其 Broker 订阅（同一适配器能力）。

## 2. 中间件输出形态（唯一）

中间件只有一种输出形态：**paho 直发 `output.broker`**。服务器上该 Broker 即同机
云端 Broker `127.0.0.1:41883`，与一体机上报同一 Broker、按主题前缀区分，平台经云端
端点统一订阅即可取数，不需要单独订阅中间件端口（`backend/config/middleware.json`
已不再有 `subscribe` 字段，只有 `enabled` / `base_url` / `token` / `timeout`）。

> 平台侧 `enabled` 只控制「是否用中间件管理数据源」，不影响数据从哪里收：
> 数据一律经云端 Broker 收取。

## 3. 接入步骤（标准流程）

### 步骤 0：确认中间件已就绪

```bash
# 服务器（71）上
systemctl status nengtan-middleware
curl -s http://127.0.0.1:42084/api/health | python3 -m json.tool
# 关注：bridge.broker=127.0.0.1:41883、bridge.connected=true、sources=N
```

平台侧配置（`backend/config/middleware.json`，容器内可用环境变量
`CARBON_MIDDLEWARE_URL` 覆盖，平台容器默认 `http://172.18.0.1:42084`）：

```json
{ "enabled": true, "base_url": "http://127.0.0.1:42084", "token": "", "timeout": 5 }
```

### 步骤 1：一体机侧接入与上行（现场常见形态）

1. 外部数据源通过**网线/工业总线**接入能碳一体机（盒子）；
2. 一体机把采集到的原始数据**上行**到云端 Broker（41883）的上行空间
   `ext/<源>/<设备>/telemetry`，载荷推荐 JSON：
   `{"device":"scale1","gross":55.2,"ts":1768600000000}`
   （`device` 为设备 id；非 JSON 纯数值消息也支持，属性名取主题末段）；
3. 上行空间约定为 `ext/#`：**平台不摄取**该空间，只由中间件订阅转换。

> 若外部系统自带 Broker 且不经一体机：中间件可直连其 Broker 订阅（同一 `mqtt`
> 适配器能力），此时 Broker 地址填外部系统的地址、主题填其原始主题。

### 步骤 2：平台登记数据源

平台「能碳一体机与数据源 → 数据源接入 → 注册外部数据源」：

| 字段 | 说明 | 示例 |
|---|---|---|
| 名称 | 展示用 | 一号炉烟气在线 |
| 发布前缀 box | **归属标识**，全局唯一，推荐 `ext-` 开头 | `ext-weigh` |
| 接入类型 | 当前支持 `mqtt`（外部 MQTT） | `mqtt` |
| Broker 地址/端口 | 经一体机接入时填**云端 Broker**；直连外部系统时填其 Broker | `127.0.0.1` / `41883` |
| 订阅主题 | 经一体机接入填上行空间；直连外部系统填其原始主题（支持 `+`、`#`） | `ext/scale1/#` |
| 字段改名（可选） | `{"gross":"weight"}` 把外部字段名改成平台语义名 | — |

等价 API：

```bash
curl -X POST http://127.0.0.1:40014/api/data-sources -H 'Content-Type: application/json' \
  -d '{"name":"外部秤站","type":"external","config":{"box":"ext-weigh","adapter":"mqtt",
       "params":{"broker":{"host":"10.0.0.20","port":1883},"topics":["factory/scale1/#"],
                 "fieldMap":{"gross":"weight"}}}}'
```

平台登记 = 向中间件注册一条数据源（中间件 `config.json` 持久化），失败则本地也不
落盘（状态始终一致）。

### 步骤 3：中间件侧确认

```bash
curl -s http://127.0.0.1:42084/api/sources | python3 -m json.tool   # 看 adapters
curl -s http://127.0.0.1:42084/api/types   | python3 -m json.tool   # 看可用类型
```

平台卡片点「测试连通」= 中间件真实 TCP + MQTT CONNECT 探测外部 Broker（5s 超时）。

### 步骤 4：验证数据到达

- 平台数据源卡片：`received`（累计收到）、`最近读数`、`云端设备数`、状态提示；
- 中间件日志：`journalctl -u nengtan-middleware -f`（看 adapter 连接/发布）；
- 直接看云端 Broker 上的标准主题：

```bash
# 任意装了 mosquitto 客户端/paho 的机器
mosquitto_sub -h 36.151.146.71 -p 41883 -t 'data/ext-weigh/#' -v
```

### 步骤 5：关联仿真设备（手动，不自动）

> **自动关联已取消**：历史上数据源可填 `target`（`工序::设备实例`）让首条消息自动
> 把外部设备绑到仿真工序设备，但该行为会在用户改绑后反复抢占，语义不可控。
> 现在关联一律由用户在平台手动建立：设备详情/设备接入里选择「绑定流程设备」
> （可同时设换算系数），保存即生效，不会被自动改写。

## 4. 标准数据规范（中间件输出）

**主题**：`data/{box}/{device}/{device}/{property}`
（第 2/3 段为同一设备 id，与一体机数据完全一致）

**载荷**：

```json
{"v": 55.2, "t": 1768600000000, "device": "scale1",
 "box": "ext-weigh", "prop": "weight", "src": "external"}
```

**转换规则**（`middleware/adapters/base.py`）：

| 规则 | 说明 |
|---|---|
| JSON 展平 | 嵌套 `{"a":{"b":1}}` → 属性 `a.b` |
| 设备 id | 取消息 `device/deviceId/sensor/id` 字段（可用 `deviceKeys` 改），否则用配置默认 `device` |
| 时间归一 | 取 `ts/timestamp/time`，秒/毫秒自动归一为毫秒；缺失取到达时刻 |
| 非数值跳过 | 字符串/布尔/NaN/inf 跳过并计 `skipped`（不污染曲线） |
| 字段改名 | `fieldMap` 在发布时套用 |

**启停语义**：平台侧条目 `enabled=false` → 摄取侧忽略该前缀全部消息，不建设备、
不驱动仿真；重新启用即恢复。

## 5. 模拟数据源接入（独立服务，默认开发机启动）

> 平台与中间件**都不内置**模拟生成器；模拟由独立服务 `sim-source` 提供，
> 停掉它就没有模拟数据——与真实外部系统行为一致。

```bash
# 开发机（推荐）：起模拟源（自带 Broker 127.0.0.1:41885）
bash platform/update.sh simsource start
bash platform/update.sh simsource status    # 或 logs / stop / restart / check

# 开发机中间件实例：订阅本机模拟源 → 转换 → 直发服务器云端 Broker(41883)
cd platform/cloud-deploy/middleware
python3 runner.py --config config.dev.json
```

| 模拟源 | box 前缀 | 上行主题 | 设备与测点 |
|---|---|---|---|
| 钢铁仿真 | `ext-steel` | `ext/steel/#` | 1#高炉（热风温度/鼓风量/炉顶压力/铁水温度/焦比/喷煤量）、1#转炉、1#烧结机、自备电厂 |
| 机房热控 | `ext-idc` | `ext/idc/#` | 机房A（送/回风温度/湿度/机柜功率/IT 负载）、冷冻水系统、空调机组、室外环境（含 PUE） |

模拟源服务（`sim-source`）在开发机把**整条上游**模拟出来：进程内先按外部系统原生主题
（`steel/…`、`idc/…`）发布到自带 Broker，再由内置的「一体机上行器」采集并上行到云端
Broker 的 `ext/steel/…`、`ext/idc/…`，随后由中间件转换为 `data/ext-steel/…`、
`data/ext-idc/…` 才被平台消费——与「外部数据系统 → 能碳一体机 → 云端」的真实链路一致。

服务器（71）的中间件 `config.json` **不采集模拟数据**（`adapters` 为空），
模拟数据由开发机中间件转换后并入服务器云端 Broker，生产与开发平台都能看到。
需要服务器侧也跑模拟时：`bash platform/update.sh simsource --server root@36.151.146.71 deploy`。

## 6. 部署与运维

```bash
# 首次/全量部署中间件到服务器（71）
bash platform/cloud-deploy/middleware/deploy_middleware.sh --server root@36.151.146.71
# 日常只更新中间件代码
bash platform/update.sh middleware
```

| 项 | 值 |
|---|---|
| 安装目录 | `/opt/nengtan-middleware`（源码在 `middleware/` 子目录，venv 在外层） |
| 服务 | `nengtan-middleware`，日志 `journalctl -u nengtan-middleware -f` |
| 管理 API | `42084`（服务器需放行：`ufw allow 42084/tcp`） |
| 数据出口 | external 形态直发同机 `127.0.0.1:41883`，无需额外数据端口 |
| 平台侧环境变量 | `CARBON_MIDDLEWARE_URL=http://172.18.0.1:42084`（容器→宿主，见 docker-compose） |

> 端口规范：项目服务端口一律 **40000+**（41883 Broker / 42084 管理 API / 41885 模拟源），
> 被占用时 +1 递增，不回落到低位端口。

## 7. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| 平台卡片「中间件服务不可达」 | 中间件进程未起 / 平台 `base_url` 不对（容器内应为 `http://172.18.0.1:42084`）/ 42084 未放行 |
| 「中间件未注册该数据源」 | 中间件重建过：平台点「同步中间件」或重新保存条目触发补注册 |
| 中间件在线但 `received=0` | 中间件没连上外部 Broker（看 `last_error`）；或平台订阅端点未启用；数据出口/订阅形态不匹配（external 应 `subscribe=false`） |
| 有数据但没显示设备 | 前缀与平台登记的 `box` 不一致；或消息没有 `device` 且未配默认 `device` |
| 中间件在收数据，平台没有 | 中间件输出主题必须是 `data/ext-*/…`：平台**不摄取**上行空间 `ext/#`（原始上行只给中间件） |
| 一体机上行后平台出现重复数据 | 检查是否把 `ext/#` 也纳入了平台摄取（应跳过）；或中间件同时订阅了上行空间与标准空间造成回环 |
| 数据进了时序库/不该进 | 服务器 collector 会忽略 `ext-*` 前缀（外部数据不入一体机时序库） |
| 一体机设备数变多 | 已修：外部源设备不再计入一体机「云端设备数」 |
| 模拟数据突然没了 | `sim-source` 服务停了（开发机 `bash platform/update.sh simsource status`） |
